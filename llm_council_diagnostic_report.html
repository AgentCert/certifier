AgentCert Certification Pipeline - Architecture Analysis & Rewiring Proposal

Generated: May 29, 2026

📋 Executive Summary

⚠️ Critical Issue Identified: LLM Council outputs are being incorrectly consumed in the certification report, resulting in misaligned findings between:
  • Section 3.1: Response & Reasoning Quality
  • Section 3.2: Safety & Compliance (RAI + Security)
  • Section 3.3: Hallucination Assessment
📊 Impact Analysis:
  • High Narrative consistency issues across report sections
  • High Graph data not aligned with textual findings
  • Medium Increased LLM token costs due to redundant council calls
  • Medium Phase 2 → Phase 3 data flow inefficiencies
✅ Proposed Solution: Architectural rewiring to consolidate RAI findings synthesis in Phase 3 (cert_builder) instead of Phase 2 (aggregator), with LLM Council removed from the critical certification path.

🏗️ Current Architecture Analysis

Pipeline Overview

Phase 0: Fault Bucketing fault_analyzer/ — Classifies trace events into per-fault lifecycle buckets
Phase 1: Metrics Extraction metrics_extractor/ — Extracts quantitative + qualitative metrics per fault
Phase 2: Aggregation ⚠️ ISSUE HERE aggregator/ — Runs LLM Council to synthesize textual metrics
# LLM Council synthesizes these metrics: - rai_check_summary - overall_response_and_reasoning_quality - security_compliance_summary - agent_summary - sensitive_data_exposure_notes
Phase 3: Certification cert_builder/ — Consumes LLM Council outputs but generates independent narratives

LLM Council Implementation

📍 Location: aggregator/scripts/llm_council.py

Component Function Issues Identified
LLMCouncil.synthesize_textual_metric() Runs k judges + meta-judge reconciliation ⚠️ Results not properly consumed downstream
LLMCouncil.compute_textual_aggregates() Synthesizes 5 textual metrics across all runs ⚠️ Duplicate synthesis in Phase 3
LLMCouncil._run_meta_judge() Reconciles judge outputs into consensus ⚠️ Inter-judge agreement not validated

Data Flow Issue

# CURRENT FLOW (PROBLEMATIC): Phase 2 Aggregator: → LLM Council synthesizes rai_check_summary → Output: {"consensus_summary": "...", "severity_label": "Strong", ...} Phase 3 Cert Builder: → Receives rai_check_summary from Phase 2 → BUT also runs independent LLM call for RAI section → Result: TWO DIFFERENT narratives for same concept → Graph/table uses Phase 2 data, text uses Phase 3 data

🔬 Root Cause Analysis

Issue #1: Architectural Misalignment

Symptom: LLM Council outputs in Phase 2 are not consistently consumed by Phase 3 narrative builders.

Root Cause: Phase 3 builders generate independent narratives instead of using Phase 2 synthesized findings.

Evidence:

# cert_builder/scripts/narratives/fault_analysis_builder.py:153-156 for key, heading in [ ("overall_response_and_reasoning_quality", "Response & Reasoning Quality"), ("security_compliance_summary", "Security Compliance"), ("rai_check_summary", "RAI Compliance"), ]: block = t[key] # ← Reads from Phase 2 lines.append(f" {heading}:") lines.append(f" Rating: {block['severity_label']}") # BUT: This is only used for CONTEXT building, not final output

Issue #2: Duplicate LLM Calls

Symptom: High token costs and latency in certification pipeline.

Root Cause: Phase 2 runs k-judge council (3 judges + 1 meta) per metric, then Phase 3 runs additional LLM calls.

Token Waste Calculation:

Metric Phase 2 Calls Phase 3 Calls Total
rai_check_summary 4 (3 judges + 1 meta) 1 (rai_builder.py) 5 calls
overall_response_and_reasoning_quality 4 1 (qualitative_findings.py) 5 calls
security_compliance_summary 4 1 (qualitative_findings.py) 5 calls
Total per fault category: 15 LLM calls

Cost Impact Estimated 3x token cost compared to optimal architecture

Issue #3: Narrative Consistency

Symptom: Graph severity labels don't match textual findings in Section 3.

Root Cause: table_builder.py uses Phase 2 `severity_label`, but narrative builders use independently generated text.

Example Mismatch:

Section 3.2 Safety & Compliance:
• Graph shows: "[Good] Strong RAI compliance: 100% RAI and 100% security compliance"
• Text says: "[Concern] Hallucinations present in all areas..."

Why? Graph uses rai_check_summary.severity_label from Phase 2, text generated independently in Phase 3.

Issue #4: Missing Validation

Symptom: No inter-judge agreement validation or fallback handling.

Root Cause: inter_judge_agreement field exists but never validated against thresholds.

# aggregator/scripts/llm_council.py:218-223 meta_response, meta_usage = await self._run_meta_judge(...) # ❌ NO VALIDATION of inter_judge_agreement # ❌ NO FALLBACK if agreement < threshold (e.g., 0.5) # ❌ NO LOGGING of low-confidence outputs

🔧 Proposed Architectural Rewiring

Core Principle: Move all narrative synthesis to Phase 3 (cert_builder). Phase 2 (aggregator) should only compute deterministic numeric aggregations and pass raw per-run textual data forward.

New Architecture

Phase 2: Aggregator (STREAMLINED)
  • ✅ Compute numeric aggregations (mean, median, p95, rates)
  • ✅ Compute boolean aggregations (PII flags, compliance flags)
  • ✅ Compute derived rates (detection rate, mitigation rate, etc.)
  • ✅ Pass through raw per-run textual data (notes, summaries)
  • ❌ Remove LLM Council textual synthesis
Phase 3: Cert Builder (ENHANCED)
  • ✅ Receive numeric aggregations + raw textual data from Phase 2
  • ✅ Run consolidated RAI findings LLM call (single call per category)
  • ✅ Generate all narratives in narrative_builders (6 builders)
  • ✅ Ensure graph data sources match narrative data sources
