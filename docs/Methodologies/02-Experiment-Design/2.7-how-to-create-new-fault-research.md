# How to Create a New Fault in AgentCert (ace-monorepo)

This document inventories every supported method for introducing a new fault into the AgentCert platform (https://github.com/AgentCert/ace-monorepo), with file paths, schemas, examples, registration, execution, and validation for each.

## Scope and Success Criteria

* Scope: ace-monorepo and its submodules — `AgentCert`, `chaos-charts`, `agent-charts`, `app-charts`, `agent-sidecar`, `flash-agent`, `litmus-go`, `certifier`, `agentcert-stack`; local Fault Studio design docs.
* Assumptions:
  * The reader has the monorepo cloned with submodules (`git submodule update --init --recursive`).
  * The local stack (MongoDB, Langfuse, LiteLLM, AgentCert, Certifier) is up via `./scripts/start-local-services.sh` and `scripts/azure_build/start-agentcert-v2.sh`.
  * A reachable Kubernetes cluster is configured for the install-agent / chaos workflows.
* Success Criteria:
  * Every fault-creation surface in the platform is enumerated.
  * Each method has authoring location, schema, minimal example, registration flow, execution path, and a smoke test.
  * Conventions (naming, versioning, RBAC, env vars, hub sync) are captured once in a cross-cutting section.

### Artifacts included are - 

* `chaoscenter/graphql/server/pkg/chaoshub/service.go`
  * `CreateChaosHubRequest` shape, `DefaultPath = "/tmp/"`, `DefaultHubSyncTimeInterval = 6h`, default-hub UUID `6f39cea9-6264-4951-83a8-29976b614289` special case, `RecurringHubSync()`.
* `chaoshub-faults/e67619df-6932-4a5c-9539-c8116d02144f/sampletest/faults/kubernetes/pod-network-loss/`
  * Live example of the three-file per-fault contract (`fault.yaml`, `engine.yaml`, `pod-network-loss.chartserviceversion.yaml`).
* `chaoshub-faults/.../faults/kubernetes/{kubernetes.chartserviceversion,experiments}.yaml`
  * Category-level CSV and generated experiments list that every new fault must be added to.

### Github Path - 

* GitHub raw fetches for `install-agent` chart (`fault.yaml`, `engine.yaml`, chartserviceversion).
  * Source: [chaos-charts install-agent fault.yaml](https://raw.githubusercontent.com/AgentCert/chaos-charts/master/faults/kubernetes/install-agent/fault.yaml)

  * Source: [litmus-go developer-guide](https://github.com/litmuschaos/litmus-go/blob/master/contribute/developer-guide/README.md)

  * Source: [AgentCert/ace-monorepo](https://github.com/AgentCert/ace-monorepo)


### Methods : Jotted below are the different ways to create a new fault.

Eight discrete creation methods cover every supported path. They are presented below in the order an author typically discovers them.

---

## Technical Scenarios

### Method 1 — Author a new ChaosHub fault (Litmus pattern, default executor)

Use this when the new fault maps to an existing `litmus-go` experiment binary. The work is purely YAML.

**Authoring location.** `chaos-charts/faults/kubernetes/<fault-name>/` with three files: `fault.yaml` (`ChaosExperiment` CRD), `engine.yaml` (`ChaosEngine` binding), and `<fault-name>.chartserviceversion.yaml` (per-fault CSV). The parent `kubernetes.chartserviceversion.yaml` and `experiments.yaml` must also list the new fault — regenerate the latter with `make combineExpCR`.

**Required fields (`fault.yaml`).** `apiVersion: litmuschaos.io/v1alpha1`, `kind: ChaosExperiment`, `metadata.name` (matches directory), `spec.definition.scope` (`Namespaced` or `Cluster`), `spec.definition.permissions[]` covering pods/events/configmaps/pods/log/pods/exec/batch.jobs/litmuschaos.io.* at minimum, `spec.definition.image` (defaults to `litmuschaos.docker.scarf.sh/litmuschaos/go-runner:latest`), `spec.definition.command` and `args` (canonical: `command: ["/bin/bash"]`, `args: ["-c", "./experiments -name <fault-name>"]`), and `spec.definition.env[]` listing tunables (`TOTAL_CHAOS_DURATION`, `RAMP_TIME`, `PODS_AFFECTED_PERC`, fault-specific knobs).

**Required fields (`engine.yaml`).** `metadata.annotations.injectionType` (AgentCert-specific, drives the Fault Studio default), `spec.engineState: active`, `spec.appinfo.{appns,applabel,appkind}` for namespaced faults, `spec.chaosServiceAccount`, and `spec.experiments[]` whose `name` matches the experiment.

**Required fields (per-fault CSV).** `metadata.version` (convention `0.1.0`), `metadata.annotations.{categories,vendor}`, `spec.displayName`, `spec.categoryDescription`, `spec.keywords`, `spec.platforms`, `spec.maintainers`, `spec.experiments`, `spec.minKubeVersion`.

**Minimal example.**

```yaml
# faults/kubernetes/pod-coffee-break/fault.yaml
apiVersion: litmuschaos.io/v1alpha1
kind: ChaosExperiment
metadata:
  name: pod-coffee-break
  labels:
    name: pod-coffee-break
    app.kubernetes.io/part-of: litmus
    app.kubernetes.io/component: chaosexperiment
spec:
  definition:
    scope: Namespaced
    permissions:
      - apiGroups: [""]
        resources: ["pods","events","configmaps","pods/log","pods/exec"]
        verbs: ["create","delete","get","list","patch","update","deletecollection"]
      - apiGroups: ["batch"]
        resources: ["jobs"]
        verbs: ["create","list","get","delete","deletecollection"]
      - apiGroups: ["litmuschaos.io"]
        resources: ["chaosengines","chaosexperiments","chaosresults"]
        verbs: ["create","list","get","patch","update","delete"]
    image: "litmuschaos.docker.scarf.sh/litmuschaos/go-runner:latest"
    imagePullPolicy: Always
    command: ["/bin/bash"]
    args: ["-c", "./experiments -name pod-coffee-break"]
    env:
      - { name: TOTAL_CHAOS_DURATION, value: "60" }
      - { name: BREAK_DURATION_SECONDS, value: "10" }
      - { name: PODS_AFFECTED_PERC, value: "" }
```

**Registration.** Commit to `chaos-charts`; the GraphQL server re-syncs the default hub every 6 h (or on demand via `syncChaosHub`). The fault then appears in the Experiment Builder.

**Execution path.** Experiment Builder → Argo `Workflow` → subscriber applies the CRs → chaos-operator spawns chaos-runner → runner launches the experiment job → `./experiments -name <fault-name>` dispatches into the Go executor.

**Smoke test.** `kubectl apply -n sock-shop -f fault.yaml -f engine.yaml`; watch `kubectl get chaosresults -n sock-shop`. Then run the full E2E and confirm a bucket appears under `certifier/workspace/<agent>/<exp>/fault-bucketing/<run>/fault_buckets/`.

**Pitfalls.** Mismatched naming (directory ≠ `metadata.name` ≠ `-name`); forgetting to append to the parent CSV / regenerate `experiments.yaml`; `Cluster` scope requires `ClusterRole`/`ClusterRoleBinding`; the certifier needs the fault to slot into `certifier/configs/fault_categories.json` (`application_fault | network_fault | resource_fault`) or metrics extraction degrades.

#### Considered Alternatives

Direct workflow embedding (pasting a `ChaosEngine` into a workflow without a hub entry) works but bypasses the Experiment Builder and Fault Studio — discouraged.

### Method 2 — Add a `litmus-go` executor for a new fault family

Use this when no existing executor binary handles the desired fault. Pairs with Method 1.

**Authoring location.** `litmus-go/experiments/<category>/<fault-name>/{experiment,test,rbac.yaml,README.md}` plus `litmus-go/chaoslib/litmus/<fault-name>/lib/<fault-name>.go`. Scaffolded with the Litmus SDK: `cd contribute/developer-guide && go build -o ./litmus-sdk ./bin/main.go && ./litmus-sdk generate experiment -f attributes.yaml -t exec|helper|aws|vmware|azure|gcp`.

**Schema (`attributes.yaml`).** `name`, `version`, `category`, `description`, `keywords`, `platforms`, `scope`, `auxiliaryappcheck`, `permissions[]` (RBAC verbs by apiGroup/resource), `maturity`, `provider`, `maintainers`, `minkubernetesversion`.

**Minimal example.**

```yaml
# litmus-go/contribute/developer-guide/attributes.yaml
name: "pod-coffee-break"
version: "0.1.0"
category: "generic"
description: "Sleeps PID 1 of the main container for a configurable duration."
keywords: ["pods","kubernetes","generic","exec"]
platforms: ["Minikube","GKE","EKS"]
scope: "Namespaced"
auxiliaryappcheck: false
permissions:
  - apigroups: ["", "batch", "apps", "litmuschaos.io"]
    resources: ["jobs","pods","pods/log","events","deployments","pods/exec","chaosengines","chaosexperiments","chaosresults"]
    verbs: ["create","list","get","patch","update","delete","deletecollection"]
maturity: "alpha"
provider: { name: "AgentCert" }
maintainers:
  - { name: "agentcert-team", email: "team@agentcert.dev" }
minkubernetesversion: "1.21.0"
```

After scaffolding, fill the `@TODO: user PRE-CHAOS-CHECK`, `@TODO: user INVOKE-CHAOSLIB`, and `@TODO: user POST-CHAOS-CHECK` markers in the generated `experiment/<fault-name>.go`, and implement `runChaos` / `experimentExecution` / `injectChaos` in `chaoslib/litmus/<fault-name>/lib/<fault-name>.go`.

**Registration.** Rebuild and publish a custom go-runner image (`make litmusgoSnapshot && docker push <registry>/go-runner:<tag>`) and reference it in Method 1's `fault.yaml` `spec.definition.image`. Adding a fault family conventionally requires PRs to **both** repos.

**Execution path.** Identical to Method 1; the dispatcher now resolves the new `-name` flag to your Go package.

**Smoke test.** The upstream developer guide uses Okteto (`okteto up` then `go run bin/go-runner.go -name <fault-name>` inside the dev pod). Follow with a full E2E run after wiring Method 1 to the new image.

**Pitfalls.** Go package name and `-name` arg must match; exec-based faults require `pods/exec` RBAC; cloud-provider faults need auth-secret env vars in the generated `engine.yaml`; keep `chaoslib/` separate from `experiments/` so it can be reused across experiments.

### Method 3 — Add an agent-lifecycle fault (`install-agent`, `install-application`, …)

Use this to treat installation (or uninstallation) of an agent or application as a first-class fault. This is the AgentCert-specific extension that distinguishes the fork from upstream Litmus.

**Authoring location.** Same as Method 1 (`chaos-charts/faults/kubernetes/<name>/`), with three key differences (verified against the live `install-agent` chart):

* `spec.definition.image` is `docker.io/agentcert/agentcert-install-agent:latest` (or `agentcert-install-app:latest`) — a `helm install` driver, not the upstream go-runner.
* `spec.definition.command` is `["/usr/local/bin/install-agent"]` with `args` of the form `[-folder=$(FOLDER), -namespace=$(NAMESPACE), -create-namespace, -timeout=$(TIMEOUT), --set=config.litellmUrl=$(LITELLM_URL), --set=config.litellmMasterKey=$(LITELLM_MASTER_KEY), --set=config.litellmModel=$(LITELLM_MODEL), --set=config.OTEL_EXPORTER_OTLP_ENDPOINT=$(OTEL_ENDPOINT), --set=config.scanInterval=$(SCAN_INTERVAL), --set=config.logLines=$(LOG_LINES)]`.
* `spec.definition.scope` is `Cluster` — the installer needs RBAC over `namespaces`, `services`, `apps/{deployments,statefulsets,replicasets,daemonsets}`, `serviceaccounts`, `secrets`, and `rbac.authorization.k8s.io/{roles,rolebindings,clusterroles,clusterrolebindings}`.

**Required env vars.** `FOLDER` (chart subdirectory under `agent-charts/` or `app-charts/`), `NAMESPACE`, `TIMEOUT`, `LITELLM_URL`, `LITELLM_MASTER_KEY`, `LITELLM_MODEL`, `OTEL_ENDPOINT`, `SCAN_INTERVAL`, `LOG_LINES`.

**Pattern.** Copy `faults/kubernetes/install-agent/` to your new `faults/kubernetes/install-agent-canary/`, change `metadata.name`, append additional `--set=` entries to `args`, add the new env vars, and update the parent CSV and `experiments.yaml`.

**Registration, execution, smoke test.** Identical to Method 1; the runner spawns the installer image, which runs `helm install` and `kubectl apply` for any extra manifests, then exits — the ChaosResult records success or failure.

**Pitfalls.** The installer image must be reachable from the target cluster (`minikube image load`, push to ACR for AKS). The `--set=` keys must match the chart's `values.yaml` exactly — typos silently no-op. Cluster scope means the namespaced SA cannot be reused; bind the elevated install-agent SA.

### Method 4 — Register a new (custom) ChaosHub

Use this to make your own Git-hosted catalogue of faults discoverable alongside the default hub. The hub *contents* follow Method 1; **registration** is GraphQL.

**Authoring location.** `chaoscenter/graphql/server/pkg/chaoshub/` exposes `addChaosHub` (Git-cloned), `addRemoteChaosHub` (tar/zip), `saveChaosHub`, `updateChaosHub`, `deleteChaosHub`, and `syncChaosHub`. Mongo collection: `chaosHubs`.

**Required fields (`CreateChaosHubRequest`).** `name` (unique per project; enforced by `IsChaosHubAvailable`), `repoURL`, `repoBranch` (required for `Git`), `description`, `tags`, `isPrivate` (if true, one of `(userName,password)`, `token`, or `(sshPrivateKey,sshPublicKey)`), `authType` (`none | basic | token | ssh`), `remoteHub` (free-form label).

**Minimal example.**

```graphql
mutation {
  addChaosHub(projectID: $pid, request: {
    name: "team-platform-hub"
    repoURL: "https://github.com/acme/chaos-charts-internal"
    repoBranch: "main"
    description: "Platform team's chaos catalogue"
    tags: ["internal","platform"]
    isPrivate: true
    authType: token
    token: "ghp_***"
  }) { id name }
}
```

**Registration / discovery.** On `addChaosHub`, the server inserts the row and `chaosHubOps.GitClone` materialises the repo under `/tmp/<projectID>/<hubID>/`. `RecurringHubSync()` re-pulls every 6 h. Faults appear in the Experiment Builder once `listChaosFaults(hubID, projectID)` enumerates them.

**Smoke test.** Call `listChaosFaults` and confirm one `Chart` per directory under `faults/kubernetes/`. Inspect `/tmp/<projectID>/<hubID>/` on the GraphQL pod.

**Pitfalls.** The default hub UUID `6f39cea9-6264-4951-83a8-29976b614289` is not in MongoDB; do not look it up. Restart of the GraphQL pod evicts the `/tmp/` clone, so the first `listChaosFaults` after restart is slow. `addRemoteChaosHub` uses `handler.DownloadRemoteHub` instead of git clone.

### Method 5 — Curate a fault collection via Fault Studio (GraphQL / UI; no YAML)

Use this to group existing ChaosHub faults into a named, project-scoped collection with per-fault `enabled`, `injectionConfig`, `customParameters`, and `weight`. This **composes** existing faults — it does not define a new primitive.

**Authoring location.** GraphQL SDL at `chaoscenter/graphql/definitions/shared/fault_studio.graphqls`; service at `chaoscenter/graphql/server/pkg/fault_studio/service.go`; Mongo collection `faultStudios`; web views under `chaoscenter/web/src/views/{FaultStudios,FaultStudio,CreateFaultStudioModal,AddFaultsModal}/`. Full design in [docs/FAULT_STUDIO_DESIGN.md](docs/FAULT_STUDIO_DESIGN.md).

**Mongo schema.**

```javascript
{
  studio_id, name, description, tags, project_id,
  source_hub_id, source_hub_name,
  selected_faults: [{
    fault_category, fault_name, display_name, description,
    enabled,
    injection_config: { injection_type, schedule, duration, target_selector, interval },
    custom_parameters,
    weight
  }],
  is_active, is_removed,
  audit: { created_at, updated_at, created_by, updated_by }
}
```

**GraphQL surface.** Queries — `listFaultStudios`, `getFaultStudio`, `listAvailableFaultsForStudio`, `getFaultStudioStats`, `isFaultStudioNameAvailable`. Mutations — `createFaultStudio`, `updateFaultStudio`, `deleteFaultStudio`, `toggleFaultInStudio`, `setFaultStudioActive`, `addFaultToStudio`, `removeFaultFromStudio`, `updateFaultInStudio`.

**Minimal example.**

```graphql
mutation {
  createFaultStudio(projectID: $pid, request: {
    name: "Network Faults"
    description: "Curated network-loss / latency / partition collection"
    tags: ["network"]
    sourceHubId: "6f39cea9-6264-4951-83a8-29976b614289"   # default hub
    selectedFaults: [
      {
        faultCategory: "kubernetes"
        faultName: "pod-network-loss"
        enabled: true
        injectionConfig: { injectionType: "continuous", duration: "60s" }
        weight: 10
      }
    ]
  }) { id name totalFaults enabledFaults }
}
```

**Registration / execution path.** Studios are **declarative metadata only** today. The design doc lists "Phase 10 — auto-inject enabled studio faults into the Experiment Builder" as a future enhancement; for now, studios are referenced by hand when assembling a scenario.

### Method 6 — Author a new scenario / Argo Workflow that composes faults

Use this to ship a new orchestration of existing faults (parallel vs sequential, new SUT, new baseline load, new probes).

**Authoring location.** `chaos-charts/experiments/<scenario-name>/`. Existing scenarios include `sock-shop/` (full resiliency: install-app → install-agent → load-test → parallel{pod-delete, pod-cpu-hog, pod-memory-hog, pod-network-loss, disk-fill} → uninstall), `sock-shop-single/`, `sock-shop-parallel/`, `sock-shop-sequential/`, `bank-of-anthos/`, `podtato-head/`, `namespaced-scope-chaos/`.

**Schema.** Argo `Workflow` (`apiVersion: argoproj.io/v1alpha1`) with `spec.templates[]`, `spec.entrypoint`, and `spec.arguments.parameters[]` carrying the AgentCert surface: `appNamespace`, `agentNamespace`, `litellmUrl`, `openaiBaseUrl`, `openaiModel`, `openaiApiKey`, `litellmUpstream`, `otelEndpoint`.

**Minimal example.**

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Workflow
metadata:
  name: sock-shop-memory-only
spec:
  entrypoint: run
  arguments:
    parameters:
      - { name: appNamespace,   value: sock-shop }
      - { name: agentNamespace, value: flash-agent }
      - { name: litellmUrl,     value: http://litellm.litellm.svc.cluster.local:4000/v1 }
  templates:
    - name: run
      steps:
        - - { name: install-app,   template: install-app }
        - - { name: install-agent, template: install-agent }
        - - { name: memory-hog,    template: pod-memory-hog }
        - - { name: uninstall,     template: uninstall }
```

**Smoke test.** `argo submit -n litmus experiments/sock-shop-memory-only/workflow.yaml`; `argo get`. Then trigger via the UI for the full E2E with trace and certification.

**Pitfalls.** Always inject `install-agent` / `install-application` first and `uninstall-*` last; plumb LiteLLM / OTEL parameters through every chaos step that touches the agent.

### Method 7 — Inject probes / ground-truth alongside a fault

Use this so the certifier can compare observed behaviour to a per-fault baseline rather than only computing intrinsic SLOs.

**Authoring location.** `chaos-charts` — probe definitions inside `fault.yaml` via `metadata.annotations.probeRef: '<JSON>'` (verified: `install-agent/fault.yaml` carries `probeRef: '[]'`). Optional `faults/kubernetes/<fault-name>/ground_truth.yaml` consumed by `certifier/configs/fault_categories.json` and `certifier/aggregator/`.

**Schema.** Litmus probes — `httpProbe | cmdProbe | k8sProbe | promProbe`, each with `mode: SOT | EOT | Edge | Continuous | OnChaos`, `probeTimeout`, `retry`, `interval`, and a probe-specific block.

**Minimal example.**

```yaml
metadata:
  annotations:
    probeRef: '[{"name":"sock-shop-200","type":"httpProbe","mode":"Continuous","httpProbe/inputs":{"url":"http://front-end.sock-shop:80/","method":{"get":{"criteria":"==","responseCode":"200"}}},"runProperties":{"probeTimeout":5,"interval":2,"retry":1}}]'
```

**Execution path.** The chaos-operator evaluates inline probes and streams results into the `ChaosResult` CR and Langfuse spans tagged with the probe name.

**Pitfalls.** `probeRef` is a JSON string, not a YAML block — escaping mistakes silently disable the probe. Prefer `SOT` / `EOT` / `Edge` modes; `Continuous` floods the runner logs.

### Method 8 — Ship a self-contained custom hub (faults + scenarios)

Use this to distribute a self-contained chaos catalogue. Combines Methods 4 and 6.

**Authoring layout.**

```
<your-hub>/
├── faults/kubernetes/<name>/{fault,engine,*.chartserviceversion}.yaml
├── experiments/<scenario>/{workflow.yaml, *.chartserviceversion.yaml}
├── crds/
└── service-accounts/
```

**Registration.** `addChaosHub` (Method 4).

**Pitfalls.** Every `engine.yaml` must reference a `ChaosExperiment` that exists in the same hub. If two hubs define the same `metadata.name`, the first hub listed wins in the Experiment Builder.

## Cross-cutting Conventions

### Naming

* Directory name = `metadata.name` (fault.yaml) = `metadata.name` (CSV) = `-name` arg in `args` = `engine.yaml.spec.experiments[].name`. Kebab-case throughout.
* Category directories: `kubernetes`, `aws`, `azure`, `gcp`, `load`, `spring-boot`, `vmware`.

### Versioning

* Per-fault `metadata.version: 0.1.0`. CI's `scripts/version/version_maker.sh` and `version_validator.py` bump on merge; `push.sh` auto-pushes the bump.
* Image tags: `ci-YYYYMMDDHHMMSS` plus `latest` plus `dev` for AgentCert-built images (`agent-sidecar`, `flash-agent`, `install-agent`, `install-app`, `certifier`) — set by `build-and-push.sh` and the per-component `build-*.sh` scripts.

### Hub sync

* Default hub UUID `6f39cea9-6264-4951-83a8-29976b614289` is hard-coded.
* `DefaultHubSyncTimeInterval = 6 * time.Hour`. On-disk path `/tmp/<projectID>/<hubID>/`.
* GraphQL pod restart triggers re-clone on the next `listChaosFaults`.

### RBAC

* Namespaced faults: experiment SA bound to a `Role` in the target namespace; `service-accounts/litmus-admin-rbac.yaml` provides the global admin SA.
* Cluster faults (node-*, install-agent): require `ClusterRole` / `ClusterRoleBinding`; `service-accounts/argowf-chaos-admin.yaml` is the elevated SA used by Argo.
* Fault Studio: `Owner` for mutations; `Owner | Executor | Viewer` for queries.

### Env-var conventions

* Agent-aware faults must accept `LITELLM_URL`, `LITELLM_MASTER_KEY`, `LITELLM_MODEL`, `OTEL_ENDPOINT`.
* Pod-level faults follow `TOTAL_CHAOS_DURATION`, `RAMP_TIME`, `PODS_AFFECTED_PERC`, `TARGET_PODS`, `NODE_LABEL`, `SEQUENCE=serial|parallel`, `CONTAINER_RUNTIME=containerd|docker|crio`, `SOCKET_PATH`.
* `ChaosEngine.metadata.annotations.injectionType` (AgentCert-fork only) drives Fault Studio's default `injection_config.injection_type`.

### Idempotency

* Hub sync uses `LastSyncedAt`; reruns overwrite the local clone cheaply.
* Fault Studio mutations check `IsFaultStudioNameUnique` per project — name collisions return a validation error.

### Non-method: `agent-sidecar`

`agent-sidecar` is **not** a fault-creation surface. It is a transparent LLM proxy that stamps `experiment_id`, `trace_id`, and `agent_id` onto outgoing requests for Langfuse correlation. It does not mutate request bodies, does not inject errors, and does not generate ChaosResults. Any future "agent-layer" fault (prompt injection, tool error, LLM-hop latency) would require extending the sidecar into a fault-aware proxy — that primitive does not exist yet.
