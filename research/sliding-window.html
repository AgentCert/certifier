Sliding Window for Extraction — with Inter-Window Summary

How metrics extraction currently batches spans, and how we can carry a rolling summary from one window to the next so each LLM call has the context of what came before.

1. What we do today

In metrics_extractor/scripts/metrics_extractor_from_trace.py, spans are sorted by startTime and chopped into fixed-size, non-overlapping batches. Each batch is sent to the LLM independently; results are merged at the end.

# metrics_extractor_from_trace.py — lines 357–366
def _create_batches(self, spans: List[Dict[str, Any]]) -> List[List[Dict[str, Any]]]:
    """Split spans into batches for processing."""
    sorted_spans = sorted(spans, key=lambda x: x.get("startTime", ""))
    batches = []
    for i in range(0, len(sorted_spans), self.BATCH_SIZE):
        batch = sorted_spans[i: i + self.BATCH_SIZE]
        batches.append(batch)
    return batches

The per-batch LLM call sits in _extract_batch_quantitative (lines 797–839) and _extract_batch_qualitative (lines 950–987). Both look roughly like this:

# Each batch goes to the LLM on its own — no prior context
prepared_spans = [self._prepare_span_for_llm(s) for s in batch]
prompt = self._build_quantitative_batch_prompt(batch_number, total_batches)
result, token_usage = await self.llm_client.with_structured_output(...)
The gap: batches are processed independently. If a fault starts in batch 3 and resolves in batch 5, batch 5 has no idea what happened in batch 3 — the model sees only the current 15 spans. The merge step at the end stitches metrics together, but each individual call is context-blind.

2. The change — pass a summary forward

After each window's extraction, ask the LLM (or build deterministically) a small carry-over summary: open faults still in progress, unresolved tool calls, the last error seen, running counters. Prepend that summary to the next window's prompt. The window itself stays the same size, so prompt growth is bounded.

New flow

Window 1spans 1–15
no prior context
Window 2spans 16–30
+ summary of W1
Window 3spans 31–45
+ summary of W1+W2
Window 4spans 46–60
+ summary of W1+W2+W3
Why it helps: the model can resolve cross-window faults inline (no extra reasoning during merge), correctly attribute TTR when fault start and resolve sit in different batches, and skip re-asking questions whose answers it already produced. Fewer downstream corrections in the aggregation step.

What the carry-over summary should hold

  • Open faults: {fault_id, type, first_seen_span, started_at} for anything detected but not yet resolved.
  • Pending tool calls: tool invocations whose response span hasn't appeared yet.
  • Running counters: tokens so far, retries so far, last error message.
  • Boundary span: the last span ID seen, so the model knows where it left off.

Keep it compact — target a few hundred tokens, capped. If it grows, drop the oldest closed items.

3. Concrete code changes

3.1 Carry a summary object through the loop

# new helper
def _empty_carry() -> Dict[str, Any]:
    return {
        "open_faults": [],          # [{fault_id, type, started_at, first_seen_span}]
        "pending_tool_calls": [],   # [{tool, span_id, started_at}]
        "last_error": None,
        "running_tokens": 0,
        "last_span_id": None,
        "window_index": 0,
    }

3.2 Sequential batch loop instead of parallel

# replace the gather-all pattern with a sequential walk so each window sees the prior summary
carry = self._empty_carry()
results = []
for i, batch in enumerate(batches):
    res, carry = await self._extract_batch_quantitative_with_carry(
        batch, batch_number=i + 1, total_batches=len(batches), carry=carry,
    )
    results.append(res)
Tradeoff: windows become sequential instead of parallel, so wall-time goes up. If that hurts, see the hybrid option below.

3.3 Inject the carry into the prompt

def _build_quantitative_batch_prompt(self, batch_number, total_batches, carry=None):
    base = self._base_quantitative_instructions()  # keep at the top so prompt cache hits
    carry_block = ""
    if carry and carry["window_index"] > 0:
        carry_block = (
            "\n## Context from previous windows\n"
            f"Open faults: {json.dumps(carry['open_faults'])}\n"
            f"Pending tool calls: {json.dumps(carry['pending_tool_calls'])}\n"
            f"Last error: {carry['last_error']}\n"
            f"Running tokens: {carry['running_tokens']}\n"
            f"Last span seen: {carry['last_span_id']}\n"
        )
    return f"{base}\n{carry_block}\n## Window {batch_number}/{total_batches}"

3.4 Update the carry after each call

def _update_carry(self, carry, batch_result, batch):
    # close faults that this window resolved
    resolved_ids = {f["fault_id"] for f in batch_result.get("resolved_faults", [])}
    carry["open_faults"] = [
        f for f in carry["open_faults"] if f["fault_id"] not in resolved_ids
    ]
    # add newly opened faults
    carry["open_faults"].extend(batch_result.get("new_open_faults", []))
    # swap pending tool calls based on responses observed
    answered = {r["span_id"] for r in batch_result.get("tool_responses", [])}
    carry["pending_tool_calls"] = [
        t for t in carry["pending_tool_calls"] if t["span_id"] not in answered
    ]
    carry["pending_tool_calls"].extend(batch_result.get("new_tool_calls", []))
    carry["last_error"] = batch_result.get("last_error", carry["last_error"])
    carry["running_tokens"] += batch_result.get("tokens_in_window", 0)
    carry["last_span_id"] = batch[-1].get("id")
    carry["window_index"] += 1
    self._cap_carry(carry)  # truncate to a token budget
    return carry

3.5 Extend the structured output schema

Add a few fields to whatever Pydantic model with_structured_output(...) uses today so the LLM tells us what to carry forward:

class BatchQuantResult(BaseModel):
    metrics: List[MetricItem]
    new_open_faults: List[OpenFault] = []
    resolved_faults: List[ResolvedRef] = []
    new_tool_calls: List[ToolCallRef] = []
    tool_responses: List[ToolResponseRef] = []
    last_error: Optional[str] = None
    tokens_in_window: int = 0

3.6 Cap the carry so it doesn't grow forever

def _cap_carry(self, carry, max_open=20, max_pending=20):
    carry["open_faults"] = carry["open_faults"][-max_open:]
    carry["pending_tool_calls"] = carry["pending_tool_calls"][-max_pending:]
    if carry["last_error"] and len(carry["last_error"]) > 300:
        carry["last_error"] = carry["last_error"][:300] + "..."

4. Variants worth considering

VariantHowWhen it fits
Pure sequential One window at a time, carry passed forward. Default. Strongest cross-window correctness.
Overlapping windows Add a small stride overlap (e.g., 15 spans, stride 12 → 3-span overlap). Dedupe on span ID. Cheap alternative if you don't want the carry plumbing but want fewer boundary misses.
Hybrid (chunked parallel) Process N windows in parallel without carry, then a "stitch" pass walks the open-fault set across chunk boundaries only. Large traces where wall-time matters more than per-call accuracy.
Deterministic carry Build the open-fault / pending-tool list from OTel span attributes (no LLM), only the LLM does extraction. Once spans follow OTel GenAI semconv (see options.html #4) — cheapest and most reliable.

5. What to watch

  • Prompt cache hits. Keep the static instructions first, then the carry block, then the window. The static prefix stays cacheable.
  • Carry token budget. Log carry size per window. If it consistently nears the cap, the cap is too low.
  • Wall-time. Sequential walk hurts here. Measure before / after; if it's bad, go hybrid.
  • Aggregation logic. The final merge step gets simpler — it can stop re-resolving cross-batch faults, since each window already did it.

6. What happens if we shrink the batch size?

A smaller batch looks like a cheaper bill — fewer spans per call, smaller prompt. In practice it usually costs more and the report quality goes down. Here's the customer-facing view of the trade-off.

The business trade-off

What you'd hope forWhat actually happens
Cost Lower — smaller prompts. Often higher. The fixed instructions get re-sent on every call, so doubling the call count roughly doubles that overhead.
Speed Faster — smaller chunks. Slower end-to-end. More calls means more network round-trips and more chance of throttling / retries.
Reliability Same. Lower. Every extra call is another chance for a transient failure.
Report quality Same. Lower for any metric that spans more than a few events (see below).

Which numbers in the certification report get hurt

MetricImpact
Time-to-detect / time-to-resolve Highest risk. A fault can start in one batch and resolve in another, so the duration is harder to compute correctly.
Tool / API success rate A call and its response can fall into different batches, making good calls look like failures.
Retry counts Retries get scattered across batches and undercounted.
Root-cause narrative With less context per call, the report reads generically ("an error occurred") instead of specifically.
Open vs. resolved faults More faults look "still open" at the end simply because the resolution sat in a later batch.
Token / latency totals Largely unaffected — these add up cleanly regardless of how the data is chunked.

How to deal with it

  1. Don't shrink blindly. Pick a batch size that fits a whole fault lifecycle, not an arbitrary number of events.
  2. Add a small overlap between batches so events near the boundary aren't cut in half.
  3. Carry a short summary forward (the pattern in sections 2–3) so each batch knows what's still open from before.
  4. Measure, then tune. Track cost and the count of unresolved-at-end faults. If the unresolved count climbs as you shrink, you've gone too small.
Bottom line: the right batch size is the smallest one that still captures a typical fault end-to-end. Going below that saves a little on each call but costs more overall — in money, time, and report accuracy.
