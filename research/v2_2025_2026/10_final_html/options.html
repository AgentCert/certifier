AgentCert — Token Optimization Options

Things we can try in the Certifier (fault bucketing + metrics extraction) and on the Langfuse side. Ordered easy → hard.

Certifier

Goal: bring down the GPT-4 bill in fault_analyzer/ and metrics_extractor/.

1 Check if prompt caching is actually working Easy

First thing to do — verify whether our prompts are even hitting the cache. The static parts (taxonomy, schema, few-shot examples) need to sit at the front of the prompt and stay identical byte-for-byte. If we're reshuffling them per call, we get nothing.

  • Restructure: [static system + taxonomy + examples] first, dynamic trace last.
  • Log cached_tokens from the API response to see hit rate.
  • Both Anthropic and OpenAI/Azure cache prefixes ≥ ~1024 tokens.
Sources: OpenAI Prompt Caching Anthropic Prompt Caching Azure OpenAI caching

2 XGrammar / structured outputs Easy

Force the LLM to emit only valid JSON against our Pydantic schema. This kills retry loops on malformed output and stops the model from adding filler prose. Already supported in Azure OpenAI via response_format, so it's mostly a flag flip.

  • Phase 0: constrain to the FaultBucket schema we already have.
  • Phase 1: use enum fields (severity, status) so the model can't drift.
  • Phase 2 judges: lock to {score, rationale} so the meta-judge parser stops breaking.
Sources: XGrammar (arXiv 2411.15100) OpenAI Structured Outputs vLLM structured outputs

3 Trim the prompt and batch 8–10 items per call Medium

Right now we re-send the same instructions for every event or fault. Strip the prompts down to what's actually needed, then batch — group 8–10 events for bucketing and 8–10 faults for metrics extraction into one call. The static instruction overhead gets paid once instead of N times.

  • Audit current prompts; pull anything redundant or unused into the cached prefix.
  • Batch on the request side for live runs.
  • For nightly / offline certifications, use the OpenAI / Azure Batch API (50% off, async).
Sources: OpenAI Batch API Azure OpenAI Batch FrugalGPT (arXiv 2305.05176)

4 Follow the OTel GenAI span spec Medium

If the upstream agent emits spans following the OpenTelemetry GenAI conventions, a lot of what Phase 0 / Phase 1 do with an LLM becomes a plain field read — gen_ai.usage.input_tokens, gen_ai.tool.name, gen_ai.agent.id. We'd only call the LLM where the spans genuinely don't tell us what happened.

  • Schema URL: https://opentelemetry.io/schemas/gen-ai/1.42.0.
  • Group events deterministically by agent / tool / operation; LLM is fallback, not first-pass.
  • Phase 1 numerics (tokens, latency, model) come straight from span attributes.
  • Ingest through Langfuse's native /api/public/otel endpoint — no custom parser.
Sources: OTel GenAI Spans spec OTel GenAI semconv Langfuse OTel ingestion

5 Use a cheaper model for classification Medium

Fault bucketing is essentially a classification task — we don't need GPT-4 for that. Move it to GPT-4o-mini, Claude Haiku 4.5, or Phi-4-Mini, and keep the big model around only for the cases the small one is uncertain about. RouteLLM is a clean pattern for the escalation.

  • Small model first, escalate to GPT-4 / o3-mini only when confidence is low.
  • Compare quality on a held-out set before flipping the switch.
  • Same pattern works for Phase 2 council judges.
Sources: RouteLLM (arXiv 2406.18665) Hybrid LLM (arXiv 2404.14618) Claude Haiku 4.5

6 Prompt compression + caching + constrained decoding (stacked) Medium

These three play well together: compress the dynamic context (Provence / LLMLingua-2), let the cache handle the static prefix (item 1), and constrain the output (item 2). On its own, each one is incremental; stacked, they add up.

  • Provence and LLMLingua-2 are drop-in: compress retrieved context before the LLM sees it.
  • Try it first on Phase 2 council inputs, where prompts are largest.
  • Measure end-to-end — compression has a quality cost, so it needs a guardrail.
Sources: Provence (arXiv 2501.16214) LLMLingua-2 (arXiv 2403.12968) 500xCompressor (arXiv 2408.03094)

7 Hybrid GraphRAG over a fault-pattern graph Hard

Right now we stuff the whole faults block into every Phase 0 prompt. The idea here is to build a small graph of fault patterns (fault type → expected span signatures → propagation paths) and retrieve only the relevant subgraph per trace. More work to set up, but it changes the cost curve — prompts stop growing with the taxonomy.

  • Stack to try: nano-graphrag (~1100 LOC) + Neo4j or FalkorDB + HippoRAG-2 retrieval + LightRAG for incremental updates.
  • Pre-filter cheaply: use Langfuse tags / metadata / sessions to narrow the candidate set before graph traversal.
  • Borrow patterns: MicroRCA-Agent, KnowledgeMind, GraphReader all do "compress then traverse" for RCA — worth reading.
  • Validate on the Nezha benchmark (TrainTicket / OnlineBoutique chaos data) before rolling out.
  • Main risk: KG construction cost. Mitigate by deriving most edges deterministically from OTel parent/child relations; LLM only for the fault-pattern ontology on top.
Sources: HippoRAG-2 (arXiv 2502.14802) LightRAG (arXiv 2410.05779) HybridRAG (arXiv 2408.04948) GraphReader (arXiv 2406.14550) nano-graphrag LightRAG repo FalkorDB Neo4j LLM-KG-Builder

8 Fine-tune a BERT or small LM for fault classification Hard

The biggest long-term lever, but the most work. Once we have enough labeled data, a fine-tuned encoder (BERT, DeBERTa, DistilBERT) or a small LM (Phi-3-Mini, Qwen 0.5B) can do the classification at a fraction of the GPT-4 cost. The trick is keeping it generic — train on span attributes, not on hard-coded fault names, so new fault types don't require retraining from scratch.

  • Bootstrap labels from current GPT-4 outputs (distillation).
  • Features: OTel span attributes (name, status, error type, parent), not raw fault strings.
  • Keep LLM as fallback for unseen / novel fault signatures.
  • Plan for re-training cadence and a confidence threshold for fallback.
Sources: DistilBERT (arXiv 1910.01108) Distilling step-by-step (arXiv 2305.02301) Phi-3 Technical Report (arXiv 2404.14219) HF fine-tuning guide

Langfuse

Push as much of the classification and extraction work into Langfuse as we can. The Certifier then only does what Langfuse can't.

1 Do classification & extraction in Langfuse; Certifier picks up the rest Medium

Langfuse v3 already has the primitives we'd otherwise rebuild — managed LLM-as-Judge evaluators, tags/metadata for span classification, Datasets for ground truth, and OTel GenAI ingestion that captures tokens and tool calls as structured fields. Run those on ingestion, and the Certifier becomes a much thinner layer that handles only aggregation across runs and the final narrative.

  • Classification: Langfuse managed evaluators (boolean / categorical / numeric) tag spans on the way in — Phase 0 just reads the tags.
  • Extraction: OTel gen_ai.usage.* attributes are captured automatically — Phase 1 reads them as-is.
  • Qualitative scoring: evaluator templates produce per-span scores; Phase 2 aggregates them.
  • Certifier scope shrinks to: Phase 2 (stats + council) and Phase 3 (narrative).
Sources: Langfuse LLM-as-Judge Langfuse OTel ingestion Langfuse Datasets Langfuse v3 changelog
