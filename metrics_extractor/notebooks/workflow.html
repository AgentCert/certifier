§1 — Observe

per (run, category, sub_fault)

Each measurement is tagged with a status based on its raw value and whether an SLA exists.

StatusConditionIn score pool?
VALIDraw > 0 and SLA presentyes
MISSINGraw is Noneyes — score 0
INVALID_ZEROraw ≤ 0yes — score 0
NO_SLASLA is nullno (diagnostics only)
Key output · status — gates every downstream calculation; misclassifying here corrupts every later grain.
Feeds §2 · only VALID rows get normalized; MISSING / INVALID_ZERO short-circuit to 0; NO_SLA is dropped from all pools.

§2 — Normalize

VALID rows only

Map each raw value to a [0, 1] score via a piecewise SLA-aware curve. Within-SLA decays gently; breach penalises hard.

ratio = raw / sla
score = (ratio ≤ 1) → 1 − 0.85·ratio
score = (ratio > 1) → max(0, 0.15 − 0.3·(ratio − 1))

Anchors: 0s → 1.00 · SLA → 0.15 · 1.5×SLA → 0.00. A miss (0) and a severe breach (0) collide on purpose — both are operationally unacceptable; detection_rate distinguishes them.

Key output · normalized_score ∈ [0,1] — the only number §3/§4/§5 ever aggregate. Raw seconds never cross grain boundaries.
Feeds §3 · scores get pooled per sub-fault; the normalization is what makes mixing pod-cpu-hog (SLA 120s) with pod-network-loss (SLA 180s) meaningful.

§3 — Sub-fault grain

e.g. pod-cpu-hog across runs

Pool all observations per sub-fault (misses kept as 0, NO_SLA excluded). Aggregate with a percentile-weighted score that focuses on the worst tail — confidence label scales with sample size.

nConfidenceScore formula
< 3INSUFFICIENTnone — raw values only
< 5LOWmean(scores)
< 20MEDIUM0.7·median + 0.3·p5
≥ 20HIGH0.5·median + 0.3·p5 + 0.2·p1
Key outputs · weighted_score (headline) + confidence (trust) + sla_compliance (raw signal). Never read one alone.
Feeds §4 · the raw obs pool flows to §4 (not the weighted_score). §3 is a view on the same pool §4 will re-group.

§4 — Category grain

e.g. resource_fault

Pool every observation across all sub-faults in the category. category_score = median(pooled scores).

Why median, not mean? Three reasons:
  • Robust to outliers. A single severe breach (score 0) or a few misses don't pull the headline down disproportionately — mean would.
  • Hits a real observation. Median is a value that actually occurred; mean is a synthetic midpoint that may match nothing in the data.
  • Bimodal-safe. When a category has half perfect runs + half misses, mean reports a misleading "average" (~0.3). Median reports either the good half or the bad half — a customer can tell which side they're on.
Mean is computed at §5 — but only as a diagnostic to flag distribution skew, never as the headline.
Key outputs · category_score (headline) + detection_rate + sla_compliance. Pooled-obs median ensures every observation gets equal weight, so rare sub-faults aren't drowned by frequent ones.
Feeds §5 · two channels: (a) the raw obs pool → §5's headline median, (b) the per-category scores → §5's mixed_category_health diagnostic.

§5 — Cumulative (agent-level)

one headline number

Pool every observation across every category. Headline is the median; reliability concerns are collapsed into a single quality_flags list so the customer view stays clean.

ColumnMeaning
cumulative_scoremedian of all pooled obs (headline)
detection_rateVALID / attempted
sla_complianceVALID ∧ within-SLA / attempted
n_attemptedobs in pool (excl. NO_SLA)
quality_flags['none'] when trustworthy, else lists what to worry about

quality_flags vocabulary: skewed_distribution |mean − median| > 0.15 (long tail of misses or breaches) · mixed_category_health |mean(category_scores) − median| > 0.15 (one category dominates) · N_obs_excluded_no_sla some obs had no SLA

Key output · cumulative_score + quality_flags together. A high score with empty flags = ship it. A high score with flags = read §4 before trusting.
Terminal stage · this is what the customer sees. Every preceding step exists to make this one number defensible.
